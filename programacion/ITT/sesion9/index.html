A propósito de los tests…

Para entrar en el tema, un chiste muy conocido entre programadores.
Un tester, alguien cuyo trabajo es probar programas, entra en un bar y pide una cerveza. Es el caso normal: lo que todo el mundo prueba, y casi siempre funciona.
Pide tres. Varias: también lo normal. Sigue funcionando.
Pide cero cervezas. El cero es un clásico: divisiones entre cero, bucles que no se ejecutan, contadores que no se incrementan.
Pide menos una. Un valor que no tiene sentido en el problema, pero que el programa puede recibir.
Pide 99999999. ¿Hay un máximo? ¿Qué pasa al pasarlo?
Pide un lagarto: ni siquiera es una cerveza. Datos de otro tipo.
Pide «asdfghjk»: basura, lo que sale al aporrear el teclado.
Y el remate: el día de la inauguración entra el primer cliente de verdad, pregunta dónde está el baño, algo que a nadie se le ocurrió probar, y el bar sale ardiendo. Los fallos no están en el caso normal, sino en los raros. Vamos a verlo con un ejemplo más serio.

El foco del testing ha de estar en los valores excepcionales

Un ejemplo fuera de la programación de la asignatura: una tienda online que vende alcohol y pide la edad. Tenemos que probar ese campo. ¿Qué escribiríais? Lo primero que hace todo el mundo: un 25. Funciona, se vende.
Un 50: también bien. Con esto parece que funciona… pero no hemos probado casi nada: los dos van por el mismo camino.
Un 15: no se puede vender alcohol a un menor, y la web lo rechaza. Ya probamos el otro camino. Y aquí hay una frontera que habría que mirar: 17 y 18.
Un 450: nadie tiene 450 años. No es una edad válida, y la web lo dice. Hasta aquí, lo que tenía pensado quien lo programó.
Ahora empiezan los raros. Un -19. Lo correcto: no es una edad válida. Pero si alguien solo comprueba «menor que 18», lo tomaría por un menor; y si solo comprueba «mayor que 120», lo daría por bueno. Depende de cómo esté escrito el if.
1.4: un número con decimales. Lo correcto es rechazarlo: no es una edad válida. Pero ojo, si se lee como entero, se quedaría en 1, y con un 18.9 habría que pensar qué hacer.
JUAN: ni siquiera es un número; tampoco es una edad válida. En C++, si leéis un int con cin y el usuario escribe letras, cin falla y la variable no tiene lo que esperáis. Probadlo algún día.
Y el último: alguien que escribe una orden de base de datos en el campo, a ver si el programa la ejecuta. Lo que debe pasar: no es una edad válida, y punto. Es un ataque real, se llama inyección SQL, y ha tumbado webs de verdad. No es para esta asignatura, pero ilustra la idea: el usuario puede escribir cualquier cosa.
La moraleja: probar no es ver que funciona con los valores normales, que casi siempre funcionan. Es buscar dónde falla. Los fallos están en los valores raros, en inglés edge cases. Ahora lo mismo con números.

Típicos: uno de cada lado. Pasan… y prueban poco

La frontera: si alguien escribe nota > 5, solo lo pilla la prueba con el 5

Los extremos del rango: el primero y el último valor válidos

Fuera de rango: ¿qué dice la PRE? Si la PRE los excluye, no hace falta probarlos

Ahora en serio, con un ejemplo de una línea: aprobado si la nota es mayor o igual que 5. Notas enteras de 0 a 10. ¿Qué valores probaríais?
Lo primero que se le ocurre a todo el mundo: un 2 y un 8, uno suspenso y otro aprobado. Están bien, pero pasan casi con cualquier código parecido.
Donde están los fallos es en la frontera: el 4 y el 5. El error típico es poner > en vez de >=. Con el 2, el 8, el 0 o el 10 ese error no se nota; solo con el 5. Por eso, en cada comparación del código, probad el valor justo de la frontera y el de al lado.
Los extremos: el 0 y el 10, el primer y el último valor válidos. En los vectores, el equivalente es la primera y la última posición.
Y fuera de rango: un -1 o un 11. Aquí manda la PRE. Si la PRE dice que la nota está entre 0 y 10, quien llama se compromete a no pasar otra cosa, y no hace falta probarlo. Si la PRE no lo dice, el módulo debe hacer algo razonable y hay que probarlo.

Lo mismo en un vector, con una prueba que ya tenéis en el proyecto: pruebaPertenece. Rellena el vector con 0, 1, 2… hasta MAX-1, y busca distintos valores. Fijaos en qué valores eligió quien la hizo, porque no son al azar.
Los que sí están: el 0, que está en la primera posición; el 6, en medio; y MAX-1, en la última. Primera y última posición son los extremos del bucle: si alguien escribe i = 1 o i < MAX-1, una de estas dos pruebas falla.
Los que no están: -1, justo antes del primero; MAX, justo después del último; y 999, uno lejos. Son las fronteras por fuera. (En el comentario del .h pone -2, pero el código prueba -1.) Y fijaos en que hay pruebas para los dos resultados posibles, true y false.

Un ejemplo con tres if: notaFinal

float notaFinal ( TipoVector notas ) {
    int i;                     // índice de 0 a MAX-1
    int presentadas = 0;       // contador
    float suma = 0;            // acumulador
    bool algunaBaja = false;   // bandera
    float nota;                // resultado
    for ( i = 0; i < MAX; i++ ) {
        if ( notas[i] != -1 ) {
            suma = suma + notas[i];
            presentadas++;
            if ( notas[i] < 4 )
                algunaBaja = true;
        }
    }
    nota = suma / presentadas;
    if ( algunaBaja && nota > 4 )
        nota = 4;
    return nota;
}

PRE: cada nota entre 0 y 10, o -1 si no se presentó. Al menos una presentada

POST: la media de las presentadas; si alguna es menor que 4, como mucho un 4

Un ejemplo que no está en la práctica, sobre las notas de 10 entregas. Cada nota va de 0 a 10, y un -1 significa que no se presentó. La nota final es la media de las presentadas, pero si alguna es menor que 4, la final se queda como mucho en un 4. Ya tiene los roles de las variables, como os pedimos. Vamos a ver qué pruebas tienen sentido mirando el código.
Tiene tres if, y cada if tiene dos caminos: se cumple o no se cumple. Una buena prueba pasa por todos. El primero: si la nota no es -1, cuenta. Hay que probar notas presentadas y también algún -1.
El segundo: si la nota es menor que 4, se levanta la bandera. Hace falta alguna nota baja y alguna que no lo sea. Y aquí hay una frontera: el 4.
El tercero tiene dos condiciones con &&. Para que se cumpla, hace falta una baja y media mayor que 4. Para que no se cumpla hay dos maneras: que no haya bajas, o que las haya pero la media no pase de 4. Conviene probar las dos.
Caso 1, lo normal: todas presentadas y ninguna baja. Debe dar la media, 7. Con este caso el if 1 siempre se cumple, el if 2 nunca y el if 3 tampoco.
Caso 2: una nota baja, y la ponemos en la última posición, que es un extremo del bucle. La media es 7.4, así que debe dar 4. Pasa por los dos caminos del if 2, porque los 8 no son bajas y el 2 sí, y por primera vez se cumple el if 3.
Caso 3: todas bajas. Hay bajas, pero la media es 3: el if 3 no se cumple por la otra mitad del &&. Debe dar 3, no 4. No estrena ningún camino, pero prueba la segunda condición del &&.
Caso 4: no presentadas, y otra vez en los extremos, primera y última posición. La media de las ocho presentadas es 6. Con esto, el if 1 también pasa por su camino del no. Con estos cuatro casos hemos pasado por todos los caminos de los tres if.
Pero todavía faltan los raros. Caso 5, la frontera del if 2: un 4 no es nota baja, porque la condición es menor estricto. Debe dar 8.5, no 4.
Caso 6: lo mínimo que permite la PRE, una sola nota presentada. ¿Y si no hubiera ninguna? Se dividiría entre cero. La PRE lo excluye, por eso no se prueba; si la PRE no lo dijera, habría que tratarlo en el código y probarlo.

Ningún caso los pilla todos: hacen falta varios, y pensados

Para ver que no son pruebas de adorno: he metido a propósito fallos típicos en notaFinal y he ejecutado los seis casos con cada versión. Estos son los valores reales que salen. Primer fallo: dividir entre MAX en vez de entre las presentadas. Solo lo pillan los casos con -1, el 4 y el 6. Sin ellos, el código parece perfecto.
Menor o igual en vez de menor: solo lo pilla el caso 5, el de la frontera. Exactamente lo que vimos con el aprobado.
Comprobar la nota baja fuera del if del -1: entonces un -1 cuenta como nota baja, porque -1 es menor que 4. Lo pillan los casos 4 y 6.
Olvidar la segunda condición del &&: solo lo pilla el caso 3, el de todas bajas.
Y el clásico de los bucles: no llegar a la última posición. Lo pillan varios, entre ellos el 2, que tiene la nota baja justo al final. En el caso 6 sale -nan: como la única nota está en la última posición, no cuenta ninguna y divide entre cero.
Ninguna prueba sola detecta todos los fallos. Por eso hay que pensar los casos mirando el código y la especificación, y no poner tres vectores aleatorios.

Cómo se mete una operación nueva en el proyecto: seis pasos, siempre los mismos. Paso 1: la cabecera en lib_vector.h, con la PRE, la POST y la complejidad. Fijaos en que la PRE dice lo de «al menos una presentada»: eso es lo que nos ahorraba probar el vector todo a -1.
Paso 2: diseñar las pruebas, en lib_test_vector.h, como comentario encima de la cabecera de la prueba. Es lo que acabamos de hacer en la pizarra: qué casos, con qué vector, y qué debe dar cada uno. Mínimo tres pruebas por operación.
Paso 3: implementar la prueba en lib_test_vector.cpp, igual que las que ya hay. Esta es automática: se prepara el vector, se llama y, si no da lo esperado, se escribe un error. Las supervisadas, como las de iniciarAleatorio, muestran el vector y quien comprueba sois vosotros. Copiad el estilo de las que hay.
Paso 4, el que más se olvida: añadir la llamada en todasLasPruebas. Si no, la prueba existe pero nunca se ejecuta, y no os enteráis.
Paso 5: ahora sí, la implementación. Que vaya después tiene sentido: si pensáis las pruebas mirando vuestro código, probaréis lo que el código hace, no lo que tiene que hacer.
Paso 6: ejecutar. Esta es la salida real del proyecto con notaFinal añadida. Con el código bien, no sale ningún error. Con el fallo del menor o igual, salta el caso 5. Si se puede, enseñadlo en Eclipse.

Normas de la asignatura en los bucles

for cuando se recorre el vector entero

while cuando se puede salir antes, con una bandera

✕ Nunca: return ni break dentro de un bucle

for ( i = 0; i < MAX; i++ )
    if ( v[i] == x )
        return true;
return false;

✓ Bandera y un solo return al final

existe = false;
i = 0;
while ( i < MAX && !existe ) {
    if ( v[i] == x )
        existe = true;
    i++;
}
return existe;

Un resultado true/false se guarda en una variable y se devuelve; nada de if (…) return true; else return false;

Unas normas de la asignatura, las mismas que en teoría. El for, para recorrer el vector entero. Si se puede salir antes, por ejemplo al encontrar algo, un while con una bandera. Esta distinción la hacemos en teoría; si usáis un for con la bandera en la condición, como el pertenece del proyecto, no pasa nada.
Lo que no se puede hacer nunca: return o break dentro de un bucle. El break solo en el switch. Este código funciona, pero no se acepta.
La forma correcta: una bandera que empieza en false, el while acaba cuando se recorre todo o cuando se encuentra, y un solo return al final. Os sirve como patrón para varias de las operaciones de hoy.
Y en las funciones que devuelven true o false: el resultado en una variable, como existe aquí, y se devuelve al final. Nada de if condición return true, else return false.
